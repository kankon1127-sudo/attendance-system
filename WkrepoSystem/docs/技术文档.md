## 1. 项目概要

Wkrepo System 是面向日本企业的**月度业务门户（Monthly Business Portal）**，把员工每月要做的几件事放在一个 Web 系统里完成：

| 业务 | 说明 |
|---|---|
| 勤怠（考勤） | 按日录入上下班时间、休息时间、出勤区分（出社／在宅／有給／欠勤），自动计算实际工时和加班时间 |
| 年休（有给休假） | 提交休假申请，管理员设置年度可休天数，系统计算已休、剩余和审批中天数 |
| 交通费 | 录入旅費交通費、非課税交通費 |
| 诸经费 | 录入其他经费 |
| 月报 | 汇总当月勤怠和经费，填写工作内容后提交，走「主管承认 → 総務确认」两级审批 |
| 申请一览 | 集中查看和审批上述所有申请，保留审批历史 |
| 社员管理 | 新建、修改、启用或停用员工，设置直属上司 |
| 数据库备份 | 管理员下载或恢复整个数据库（SQL 文件） |

**界面语言**：默认日文，可切换中文（URL 参数 `?lang=zh_CN`）。

### 3.2 启动流程

1. **`H2DataLocationEnvironmentPostProcessor`**（在 Spring 容器创建之前执行，通过 `META-INF/spring.factories` 和 `META-INF/spring/...EnvironmentPostProcessor` 注册）
   - 向上查找包含 `pom.xml` 的目录作为项目根目录
   - 确定数据目录：如果设置了环境变量 `APP_DATA_DIR` 就用它，否则用 `<项目根>/data`
   - 如果数据目录里没有数据库文件，依次尝试从 `db/`、`target/db/` 复制旧数据（迁移用）
   - 删除残留的 `wkreposystem.lock.db`，避免上次异常退出导致无法连接
   - 用计算出的绝对路径覆盖 `spring.datasource.url`
2. Spring Boot 正常启动，JPA 根据实体自动建表或补列。
3. **`DataInitializer.init()`**（`@PostConstruct`）：如果不存在，就创建 5 个测试账号和对应的默认勤怠设置（见 [6.2](#62-初始账号)）。
   - 这个类是普通的 `@Component`，**没有 `@Profile` 等任何条件**，项目里也没有区分环境的配置文件，所以**生产环境每次启动都会执行**。
   - 判断条件只看「这个用户名是否存在」：账号被改名后，下次启动会用原用户名和密码 `123456` 重新创建一个账号。
   - 每次启动都会把 5 个账号的密码打印到标准输出（`app.log`），即使密码已经改过。

## 5. 数据模型

### 5.1 ER 关系

```
                      ┌──────────────┐
          managerId ┌─┤    users     │
       (自关联,上司)  └─►│              │
                      └──────┬───────┘
          ┌──────────┬───────┼─────────┬──────────────┬─────────────────────┐
          │1:N       │1:N    │1:N      │1:N           │1:N                  │1:1
   ┌──────▼─────┐┌───▼────┐┌─▼───────┐┌▼────────────┐┌▼──────────────────┐┌▼──────────────────────────┐
   │attendances ││paid_   ││travel_  ││general_     ││monthly_reports    ││default_attendance_settings│
   │            ││leaves  ││expense  ││expenses     ││ (approverId→users)││                           │
   └────────────┘└────────┘└─────────┘└─────────────┘└───────────────────┘└───────────────────────────┘
          users 1:N paid_leave_entitlements（按年）

   approval_history：用 (applicationType, applicationId) 逻辑关联到上面四类申请，没有外键
```

### 5.2 各表说明

| 实体 / 表 | 主要字段 | 说明 |
|---|---|---|
| `User` / `users` | `username`(唯一), `password`, `name`, `email`, `employeeId`(唯一), `department`, `role`, `managerId`, `status`(ACTIVE/INACTIVE) | 员工。`role` 是字符串，取值见 `Role` 枚举 |
| `Attendance` / `attendances` | `user`, `date`, `startTime`, `endTime`, `breakTime`(LocalTime 表示时长), `workHours`, `overtimeHours`, `agreement36Status`, `remarks` | 一人一天一条。`agreement36Status` 实际存的是**出勤区分**：`出社`/`在宅`/`有給`/`欠勤`/`-` |
| `DefaultAttendanceSetting` | `user`(1:1), `defaultStartTime`, `defaultEndTime`, `defaultBreakMinutes`, `defaultAgreement36Status`, `defaultApprover` | 「一键默认填入」用的模板 |
| `PaidLeave` / `paid_leaves` | `user`, `startDate`, `endDate`, `leaveDays`, `leaveType`(全日/午前/午後 等), `status` | 年休申请，默认 `PENDING` |
| `PaidLeaveEntitlement` | `user`, `year`, `grantedDays` | 年度付与天数，(user, year) 唯一 |
| `TravelExpense` / `travel_expense` | `user`, `expenseDate`, `type`(旅費交通費/非課税交通費), `transportation`, `route`, `summary`, `amount`, `status` | 交通费 |
| `GeneralExpense` / `general_expenses` | `user`, `date`, `expenseType`, `summary`, `amount`, `remarks`, `status` | 诸经费 |
| `MonthlyReport` / `monthly_reports` | `user`, `year`, `month`, `workContent`, `approverId`, `status` | 月报，默认 `DRAFT` |
| `ApprovalHistory` / `approval_history` | `applicationType`, `applicationId`, `previousStatus`, `nextStatus`, `actorId`, `actorName`, `actionAt` | 每次状态变化记一条 |

### 5.3 申请状态 `ApplicationStatus`

| 值 | 日文显示 | 用于 |
|---|---|---|
| `PENDING` | 申請中 | 交通费、诸经费、年休的初始状态 |
| `APPROVED` | 承認済 | 交通费、诸经费、年休通过 |
| `REJECTED` | 拒否 | 所有类型 |
| `DRAFT` | 下書き | 月报初始状态 / 撤回后 |
| `SUBMITTED` | 提出済 | 月报已提交 |
| `MANAGER_APPROVED` | リーダー承認済 | 月报一级审批通过 |
| `FINALIZED` | 総務確認済 | 月报最终确认 |

## 6. 角色与权限

### 6.1 角色

| 角色 | 显示名 | 概要 |
|---|---|---|
| `GENERAL` | 一般 | 只能操作和查看自己的数据 |
| `MANAGER` | 部長 | 查看并审批**同部门**的申请；只能管理本部门的一般员工 |
| `SOUMU` | 総務 | 查看全部申请；对 `MANAGER_APPROVED` 的月报做最终确认；可管理员工（不能创建 ADMIN） |
| `ADMIN` | 管理者 | 全部权限，包括默认勤怠设置、年休付与、数据库备份恢复 |

### 6.2 初始账号

由 `DataInitializer` 自动创建，密码都是 `123456`：

| 用户名 | 角色 | 社员番号 | 部门 | 上司 |
|---|---|---|---|---|
| admin | ADMIN | EMP001 | 管理部 | — |
| manager | MANAGER | EMP002 | 开发部 | admin |
| employee1 | GENERAL | EMP003 | 开发部 | manager |
| employee2 | GENERAL | EMP004 | 开发部 | manager |
| soumu | SOUMU | EMP005 | 総務部 | admin |

> ⚠ 这些账号在**所有环境**都会被创建，包括生产环境（见 [3.2](#32-启动流程)）。部署后必须立刻修改密码或停用这些账号，最好改代码让它只在开发环境运行。

### 6.3 权限检查的位置

权限检查分布在三个地方：

1. **`PermissionInterceptor`**（全局）
   - 除 `/login`、`/css/**`、`/js/**`、`/h2-console/**` 外，所有请求都要求 Session 中有用户，否则跳转 `/login`。
   - `/default-attendance-setting`、`/admin/database-backup` 开头的路径要求 `ADMIN`，否则跳转 `/home?error=permission`。
   - `MANAGER_PATHS` 目前为空（预留）。
2. **Controller 内部**：例如 `DatabaseBackupController`、`PaidLeaveController.saveEntitlement`、`UserManagementController` 自行判断角色。社员管理的 4 个入口（一览、新建、修改、启用/停用）都会把 `GENERAL` 重定向到 `/home`。
3. **Service 内部**：例如 `ApplicationListService.canApprove/canView`、`TravelExpenseService.ensureOwner`。

> 注意：所有检查使用的都是**登录时放进 Session 的 `User` 对象**，之后不会再从数据库重新读取。所以员工被停用或角色变更后，只要不重新登录，仍然按原来的状态和权限使用系统。
### 6.4 审批权限规则（`ApplicationListService.canApprove`）

- **任何人都不能审批自己的申请。**
- 交通费 / 诸经费 / 年休：状态为 `PENDING` 或 `SUBMITTED` 时，`ADMIN` 可以审批；`MANAGER` 只能审批同部门的申请。
- 月报：
  - `SUBMITTED` → `ADMIN` 可以审批；`MANAGER` 在「自己是指定审批人」或「同部门」时可以审批。
  - `MANAGER_APPROVED` → 只有 `SOUMU` 或 `ADMIN` 可以审批（最终确认）。

## 7. 各模块与主要函数

### 7.1 认证与首页 — `AuthController` / `UserService`

| 函数 | 说明 |
|---|---|
| `AuthController.loginPage()` | `GET /login`，显示登录页 |
| `AuthController.login(username, password)` | `POST /login`，调用 `UserService.login`，成功后把 `User` 放进 Session 并跳转 `/home` |
| `AuthController.logout()` | 使 Session 失效 |
| `AuthController.home()` | 首页仪表盘：待审批件数（等待 ≥7 天的算「超期」）、最早的 5 件待审批、最近 6 个月的工时和加班趋势、本月加班相对 45 小时上限的进度（≥40 小时显示警告）、今年剩余年休 |
| `UserService.login()` | 依次检查：用户存在 → 不是 `INACTIVE` → 密码一致（明文比较） |
| `UserService.createUser()` | 校验必填项，以及用户名和社员番号是否重复 |
| `UserService.updatePassword()` | 密码至少 4 个字符 |

### 7.2 勤怠 — `AttendanceController` / `AttendanceService` / `HolidayService`

**Controller**

| 函数 | URL | 说明 |
|---|---|---|
| `showAttendance` | `GET /attendance?year&month` | 生成整月日历（带节假日标记）、月度统计、异常列表、是否锁定、可选月份列表、默认设置。**不允许访问未来月份**，会重定向到当前月 |
| `saveInline` | `POST /attendance/saveInline` | 月历行内保存一天。先按 (用户, 日期) 查已有记录再更新；月份已锁定时带 `locked=true` 跳回。**工时和加班时间直接使用前端传来的值**（见下方说明） |
| `showEditPage` / `saveEditPage` | `GET /attendance/edit/{date}`、`POST /attendance/edit` | 单日编辑页（只改时间和备注）。不会清空已有的工时，所以**修改时间后工时不会重新计算**（见下方说明） |
| `getDefaultSetting` | `GET /attendance/getDefaultSetting` | 返回 JSON 格式的默认设置 |
| `bulkApplyDefaults` | `POST /attendance/bulkApplyDefaults` | 一键填入默认值，返回 JSON `{success, message}` |
| `exportMonthlyAttendance` | `GET /attendance/export?year&month` | 下载 `attendance-YYYY-MM.xlsx`。导出范围：ADMIN/SOUMU 全员，MANAGER 本部门，GENERAL 只有自己 |

**`AttendanceService` 主要函数**

| 函数 | 说明 |
|---|---|
| `createAttendance` / `updateAttendance` | 保存前依次执行：`ensureMonthEditable` → `validateAttendance` → `calculateWorkHours` → `determineAgreement36Status`。`updateAttendance` 在 ID 为空但该日已有记录时，会自动关联已有 ID，保证是更新而不是新增 |
| `isMonthLocked(user, y, m)` | 当月月报存在且状态**不是** `DRAFT`/`REJECTED` 时返回 true |
| `ensureMonthEditable` | 月份已锁定时抛出异常。交通费、诸经费的保存和删除也会调用它 |
| `calculateWorkHours` | 区分为 `-` 时工时和加班都设为 0。**只要工时和加班都不为 null 就直接返回，不做任何计算或校验**；只有缺少时才根据上下班时间计算：工时 = 下班 − 上班（跨零点加 24 小时），**不扣除休息时间**；加班 = 休息日时等于全部工时，平日时为超过 8 小时的部分 |
| `determineAgreement36Status` | 只有区分为空时才自动推断（正常／加班／深夜／休日 等）。22:00–5:00 算深夜 |
| `calculateMonthlyStatistics` | 月度统计：跳过 `-`/`欠勤`/`有給`/空；出勤天数只统计 `出社`/`在宅` 且工时 > 0 的日子 |
| `calculateMonthlyTrend` | 多个月的统计，并计算柱状图的百分比（首页用） |
| `findMonthlyAnomalies` | 检测以下异常：有时间但没有区分；出社或在宅却缺少上下班时间；休息时间超过在岗时间；有給日却有工作记录；有給日没有已批准的年休（未申请 / 审批中）；欠勤日却有工作记录 |
| `validatePaidLeaveApprovedForMonthlySubmit` | 月报提交前检查：勤怠中标为「有給」的每一天，都必须有已被主管批准的年休申请，否则列出未申请和未批准的日期并拒绝提交 |
| `bulkApplyDefaults` | 给当月所有工作日（跳过周末和节假日）中**还没有区分**的日子填入默认上下班时间、休息时间和区分（默认「出社」，休息默认 60 分钟），然后重新计算工时 |
| `validateAgreement36Rules` | 36 协定检查（月加班 45 小时、休日工作 40 小时）。**目前没有任何地方调用** |

**工时由谁计算：三条路径的结果不一致**

| 入口 | 工时的来源 | 是否扣休息 | 休息日的加班 |
|---|---|---|---|
| 月历行内保存 `saveInline` | 前端 JS `calculateWorkHours(day)` 计算后，把表格单元格里的文字作为 `workHours`/`overtimeHours` 提交；区分为 `-`/`欠勤`/`有給` 或时间不全时传 0 | 扣除 | 仍按「超过 8 小时的部分」，不区分休息日 |
| 一键默认填入 `bulkApplyDefaults` | 先把工时设为 null，再由后端 `calculateWorkHours` 计算 | **不扣除** | 全部工时 |
| 单日编辑页 `saveEditPage` | 已有记录：保留原来的工时（不重新计算）；新记录：后端计算 | **不扣除** | 全部工时 |

服务端对 `saveInline` 提交的数值**完全没有校验**：负数、超过 24 小时、与上下班时间不符、区分为「有給」却有工时，都会原样保存。直接发 POST 请求就能任意修改自己的工时和加班时间。

例：默认设置 9:00–18:00、休息 60 分钟时，行内保存得到「工时 8.00 / 加班 0.00」，一键默认填入得到「工时 9.00 / 加班 1.00」。

**`HolidayService`**

| 函数 | 说明 |
|---|---|
| `isRestDay(date)` | 周末、法定节日、振替休日或国民の休日时返回 true |
| `isNationalHoliday(date)` | 用算法判断日本的法定节日：固定日期的节日、Happy Monday（第 N 个周一）、春分和秋分（近似公式） |
| `isSubstituteHoliday` / `isCitizensHoliday` | 振替休日；夹在两个节日之间的平日 |

**`AttendanceExcelExportService.exportMonthlyAttendance`**：按社员番号排序，每人一行（社员番号、姓名、部门、出勤天数、实际工时、加班时间）。冻结表头并开启筛选。跳过 `-`/`欠勤`/`有給`/空的记录；出勤天数只统计 `出社`/`在宅`。休息日把**工时和加班相加**后全部计入加班。由于两条计算路径都已经在加班里包含了休息日的工时（见上表），这会导致**重复计算**：例如周日工作 10 小时，行内保存的数据（工时 10、加班 2）在 Excel 中算作加班 12 小时；一键填入或编辑页的数据（工时 10、加班 10）算作 20 小时。

**`calculateMonthlySummary` 的统计规则（已核实）**

- **稼働天数**：区分不为 null，且不是 `休日`/`未出勤`/`-` 的天数都会计入。UI 的选项只有 `出社`/`在宅`/`有給`/`欠勤`，而 `休日`、`未出勤` 只会在后端自动推断时出现，所以**有給和欠勤都会被算作稼働日**。
- **工时和加班**：不看区分，直接把所有记录的值相加。
- **经费**：按日期取当月的全部交通费和诸经费，**不看审批状态**，所以「拒否」和「申請中」的金额也会计入合计。

同一个月的统计，系统里有 4 种不同的算法，结果可能互相对不上：

| 位置 | 稼働 / 出勤天数 | 工时和加班 |
|---|---|---|
| 勤怠页面、首页（`AttendanceService.calculateMonthlyStatistics`） | 只统计 `出社`/`在宅` 且工时 > 0 的日子 | 跳过 `-`/`欠勤`/`有給`/空 |
| 月报及申请详情（`MonthlySummaryService`） | 除 `休日`/`未出勤`/`-` 外都计入（**包括有給和欠勤**） | 全部相加 |
| Excel 导出（`AttendanceExcelExportService`） | 只统计 `出社`/`在宅` | 跳过 `-`/`欠勤`/`有給`/空；休息日的工时也算进加班 |

例：某月出社 18 天、有給 2 天、欠勤 1 天，勤怠页面显示 18 天，月报显示 21 天。

## 8. 数据流程

### 8.1 请求处理的通用流程

```
浏览器 ─► LocaleChangeInterceptor ─► PermissionInterceptor
            (?lang=)                  (Session 中没有 user → /login)
                                      (ADMIN 专用路径检查)
      ─► Controller：从 session 取出 User
      ─► Service：业务校验 / 计算（抛出异常时，Controller 用 Flash 消息带回页面）
      ─► Repository ─► H2
      ─► Controller：填充 Model → Thymeleaf 渲染，或 redirect（PRG 模式）
```

表单提交基本都采用 **POST → Redirect → GET** 模式，错误和成功消息通过 `RedirectAttributes` 的 Flash 属性传递。

### 8.2 勤怠录入流程

```
[月历画面] 修改某一天 ─► POST /attendance/saveInline
   │
   ├─ 当月月报已提交？ ──是──► 跳回 ?locked=true（不保存）
   │
   ├─ 查出 (用户, 日期) 的已有记录，没有就新建
   ├─ 写入时间 / 区分 / 备注 / 前端 JS 算好的工时和加班（★ 服务端不校验）
   └─ AttendanceService.updateAttendance
        ├─ ensureMonthEditable（再次检查）
        ├─ validateAttendance（同一天不能有重复记录）
        ├─ calculateWorkHours（工时和加班都有值 → 直接返回，什么都不做）
        ├─ determineAgreement36Status（只在区分为空时推断）
        └─ save
```

### 8.3 月报的生命周期（状态机）

```
             saveDraft                     submit（必须指定直属上司，所有有給日都已批准）
  (无) ───────────────► DRAFT ─────────────────────────────────────► SUBMITTED
                         ▲  ▲                                          │  │
                         │  └──────────── withdraw（本人）─────────────┘  │
                         │                                              │ 部长 / ADMIN 承认
                    再编辑 │                                              ▼
                         │                                       MANAGER_APPROVED
                     REJECTED ◄──── reject（各阶段的审批人）──────────┤
                                                                       │ 総務 / ADMIN 最终承认
                                                                       ▼
                                                                   FINALIZED
```

- 状态为 `SUBMITTED` 及之后时，`isMonthLocked` 为 true，**当月的勤怠、交通费和诸经费都不能修改**。
- 每次状态变更都会通过 `ApprovalHistoryService.transition` 记录到 `approval_history`。

### 8.4 交通费、诸经费和年休的审批流程

```
员工保存 ─► status = PENDING ─► 邮件通知上司（可选）
                 │
      申请一览中由部长（同部门）或 ADMIN 审批
                 ├─ 承认 ─► APPROVED
                 └─ 拒否 ─► REJECTED
```

### 8.5 年休与勤怠的联动

```
勤怠中把某天设为「有給」
   ├─ 勤怠页面：如果没有已批准的年休 → 显示异常（未申请 / 审批中）
   └─ 提交月报时：validatePaidLeaveApprovedForMonthlySubmit
         只要有一天没有已批准的年休 → 拒绝提交并列出日期
```

### 8.6 首页仪表盘的数据来源

```
home() ─┬─ ApplicationListService.getPendingApprovalsForUser   → 待审批件数 / 超期件数 / 最早 5 件
        ├─ AttendanceService.calculateMonthlyTrend(最近 6 个月)  → 趋势柱状图、本月工时和加班
        └─ PaidLeaveService.getBalance(今年)                     → 剩余年休
```

## 10. 运行与部署

### 10.1 环境要求

- **JDK 17**（bat 脚本默认路径为 `C:\Program Files\Microsoft\jdk-17.0.21.21-hotspot`）
- 不需要单独安装 Maven（使用自带的 `mvnw`）
- 不需要单独安装数据库（内置 H2）

### 10.2 开发时运行

**方式 A：使用脚本（Windows）**

```bat
run.bat
```

脚本会依次：设置 UTF-8 编码 → **强制结束所有 `java.exe` 进程** → `mvnw clean compile` → 打开浏览器访问 `http://localhost:8080/login` → `mvnw spring-boot:run`。

> ⚠ `taskkill /F /IM java.exe` 会结束本机上**所有** Java 进程，包括 IDE 等，使用时请注意。

**方式 B：命令行**

```bash
./mvnw spring-boot:run "-Dfile.encoding=UTF-8"
```

**方式 C：IDE**

直接运行 `com.wkrepo.system.WkrepoSystemApplication` 的 `main`。

启动后访问 `http://localhost:8080/login`，使用 [6.2](#62-初始账号) 中的账号登录。

### 10.3 打包与运行 jar

```bat
package-only.bat        :: 等价于 mvnw clean package -DskipTests
run-only.bat            :: 等价于 java -jar target\wkrepo-system-1.0.0.jar
```

在其他机器上运行：

```bash
java -Dfile.encoding=UTF-8 -jar wkrepo-system-1.0.0.jar
```

| `SPRING_MAIL_USERNAME` / `SPRING_MAIL_PASSWORD` | 未设置 | SMTP 认证信息 |
| `SPRING_MAIL_PROPERTIES_MAIL_SMTP_AUTH` / `..._STARTTLS_ENABLE` | 未设置 | SMTP 选项 |
| `app.notifications.from` | 空 | 发件人地址 |
| `spring.h2.console.enabled` | true | H2 控制台，**生产环境请关闭** |
| `spring.jpa.show-sql` | true | 输出 SQL 日志，生产环境建议关闭 |
| `spring.servlet.multipart.max-file-size` | 50MB | 备份恢复时上传文件的大小上限 |

示例（Linux 服务器）：

```bash
export APP_DATA_DIR=/var/lib/wkrepo
export SPRING_MAIL_HOST=smtp.example.com
export SPRING_MAIL_PORT=587
export SPRING_MAIL_USERNAME=noreply@example.com
export SPRING_MAIL_PASSWORD=********
export SPRING_MAIL_PROPERTIES_MAIL_SMTP_AUTH=true
export SPRING_MAIL_PROPERTIES_MAIL_SMTP_STARTTLS_ENABLE=true
java -Dfile.encoding=UTF-8 -jar wkrepo-system-1.0.0.jar \
     --spring.h2.console.enabled=false --spring.jpa.show-sql=false
```

### 10.5 部署注意事项

- **数据持久化**：H2 是单文件数据库，所以 `APP_DATA_DIR` 必须指向持久存储（云平台上要挂载持久磁盘，例如 Render Persistent Disk）。
- **单实例运行**：没有使用 H2 的 `AUTO_SERVER` 模式，同一个数据库文件只能被一个进程打开，不能做多实例负载均衡。
- **Session 保存在内存中**：重启后所有用户都需要重新登录。
- **备份**：可以在社员管理画面让管理员下载 SQL 备份，也可以在停止应用后直接复制 `wkreposystem.mv.db`。
- **表结构变更**：`ddl-auto=update` 只会新增表和列，不会删除或修改已有列。生产环境建议改用 Flyway 等迁移工具。
- **HTTPS**：应用本身没有配置 TLS，建议在前面放 Nginx 等反向代理。
